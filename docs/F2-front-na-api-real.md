# F2: front na API real (partes 1 e 2 prontas em 27/10/2026)

**Situação (27/10/2026):** o back-end tem login, clientes, serviços, profissionais e agenda núcleo (CI verde). O front inteiro ainda fala com `src/services/api.js`, uma API **síncrona** que guarda o estado todo em memória e roda o motor de regras (`domain/engine.js`) no navegador.

## Por que não liguei sozinho
1. **Regra 9 do projeto:** o Artifact é um HTML sem rede, e `tests/estatico.test.mjs` proíbe `fetch(` em `src/`. Um cliente HTTP quebra essa regra no Artifact.
2. **Tamanho da mudança:** as telas leem `store.getSnapshot()` (estado completo) e chamam funções síncronas. Com a API real tudo vira assíncrono, com carregamento e erro, e o motor de regras (conflito, comissão, cupom, Pix, mensagens) precisa ir inteiro para o servidor antes de a tela depender dele. Ligar só uma parte deixaria dois "donos" do mesmo dado.

## Proposta (a confirmar)
- **Dois builds, mesma interface.** Artifact e testes continuam na API simulada (sem rede). O site publicado (`AGENDZ_DOMINIO`) usa `src/services/api-real.js`, escolhido por `define`/alias do esbuild; o arquivo com `fetch` só entra nesse build. O teste estático passa a conferir que o `dist/agenda.html` (Artifact) não tem `fetch`.
- **Migração por partes, na ordem:** `auth` (login real, token só em memória) → `clientes` → `servicos` → `equipe` → `agenda` (conflito já está no servidor). Cada parte só troca quando o servidor tem **toda** a regra daquele recurso e o teste de equivalência (simulada × real) passa.
- **Bootstrap:** `GET /api/publico/loja` (tipo, nome, logo) → carrega só a pasta do tipo.
- Enquanto isso o site em `*.agendz.io` continua sendo a demonstração (dados de exemplo no navegador).

## Parte 1 (feita): login real e bootstrap da loja
- `AGENDZ_API=real node build.mjs` (ou `node build.mjs --real`; o `npm run build` faz os dois) gera `dist/index-real.html` a partir de `src/main-real.jsx` → `src/ui/real/AppReal.jsx` → `src/services/api-real.js`. É o **único** arquivo de `src/` com `fetch`; o bundle do Artifact (`main.jsx`) não o importa (`tests/estatico.test.mjs` monta o bundle e confere que não há `fetch(` nem rota da API real).
- Fluxo: `GET /api/publico/loja` (tipo, nome, logo, tema; 404 = "Loja não encontrada", nunca loja padrão) → login (`POST /api/auth/login`) → se `deveTrocarSenha`, tela de troca (`PUT /api/usuarios/me/senha`) → painel inicial. O painel é provisório: os módulos entram nas partes seguintes.
- Token **só em memória** (sem localStorage, sessionStorage ou cookie; `credentials: 'omit'`); recarregar a página pede o login. 401 com token = sessão vencida (volta ao login). Nenhuma função lança: devolve `{ ok, erro }` com mensagem em português; mensagem do servidor só entra no formato `{mensagem}` com até 200 caracteres.
- Testes: `tests/api-real.test.mjs` (servidor falso), `tests/estatico.test.mjs`, `tests/e2e36.mjs` (navegador, servidor falso no mesmo endereço, 390 px com fonte larga).
- **Publicação:** o CI (`ci.yml`, job do site) publica a **demonstração** enquanto a variável do repositório `SITE_REAL` não for `true`. Com `SITE_REAL=true` o `index.html` do site passa a ser `dist/index-real.html`. Ligue **depois** de rodar `deploy/provisionar-loja.sh` das lojas (antes disso o site real não tem usuário para entrar). `deploy/montar-site.sh dominio --real` faz o mesmo à mão.
- Próximas partes: clientes → serviços → equipe → agenda (cada uma só com a regra inteira no servidor e teste de equivalência).

## Parte 2 (feita): clientes (v81)
- **Servidor** (`backend/.../clientes/ClienteService` + `ClienteController`; migração `V10__cliente_completo.sql`): `GET /api/clientes?q=`, `GET /api/clientes/{id}`, `POST /api/clientes`, `PUT /api/clientes/{id}` (dono e profissional; outra loja = 404). Regras = as de `clientes.salvar` da API simulada, com as mesmas mensagens.
- **Dados pessoais cifrados** (`cifra/Cifra`: AES-256-GCM, IV aleatório por valor, formato `v1:iv:texto:tag`): telefone, CPF e nascimento. Para achar e impedir duplicidade: `telefone_hash` e `cpf_hash` (HMAC-SHA256 com pepper, **amarrado à loja**). Nome e apelido em texto puro (decisão do proprietário). A chave (`CIFRA_CHAVE`) e o pepper (`CIFRA_PEPPER`) são gerados na VPS pelo `deploy/preparar-api.sh` (nunca no repositório, no log ou no banco). **Trocar a chave depois de ter clientes torna os dados ilegíveis; guarde uma cópia fora da VPS e fora do backup do banco.** A API não sobe sem as duas.
- **Duplicidade:** telefone + nome (sem diferenciar maiúsculas) = 409 "Já existe um cliente com esse nome e telefone."; o mesmo telefone com nomes diferentes é permitido (família no mesmo número). CPF único por loja = 409 "Esse CPF já está cadastrado." (nunca diz de quem). O mesmo CPF em lojas diferentes é permitido.
- **Quem vê e altera o quê:** a lista traz só o CPF mascarado e nunca o nascimento. Na ficha, CPF completo e nascimento (e trocar telefone, CPF ou nascimento) são do **dono, do profissional que atende o cliente (tem agendamento com ele) ou de qualquer um quando o cadastro ainda não tem horários**; os demais recebem 403 ao tentar alterar e `dadosCompletos: false` ao ler. Troca de telefone grava o número antigo (cifrado) e quem trocou (`cliente_telefone_anterior`).
- **Telefone:** aceita com ou sem 55 e com máscara; guarda `55`+DDD+número. Outro tamanho = "Informe o telefone com DDD.".
- **Veículos** (`cliente_veiculo`, só quando o tipo tem a capacidade `usaVeiculo`; hoje `estetica_automotiva`, em `ClienteService.usaVeiculo`): até 10, placa antiga ou Mercosul só por formato, modelo e porte obrigatórios, placa única por cliente, `id` sempre do servidor (id de outro cliente enviado vira veículo novo). Outros tipos **descartam** `veiculos`. A trava "veículo com agendamento ativo não sai" entra na parte da agenda (o agendamento real ainda não guarda o veículo).
- **Busca** (`q`): nome, apelido, telefone (DDD + número, parcial), CPF (dígitos), placa e modelo; até 500 resultados. É feita no servidor depois de decifrar (campo cifrado não se consulta no SQL); suficiente para milhares de clientes por loja.
- **Equivalência simulada × real:** `backend/src/test/resources/equivalencia/clientes.json` (28 casos de validação) roda na API simulada (`tests/clientes-equivalencia.test.mjs`) e no servidor (`ClientesEquivalenciaTest`, CI). A API simulada ganhou as regras que o mapa já prometia e faltavam: CPF válido e único, nascimento real, telefone brasileiro com DDD.
- **Tela** (`src/ui/real/Clientes.jsx`, menu Início/Clientes em `AppReal.jsx`): lista em cartões, busca, novo, editar, veículos por tipo, dados restritos (CPF mascarado, campos escondidos e fora do `PUT`). Teste de navegador: `tests/e2e39.mjs`.
- **Fora desta parte (ficam para depois):** pedidos de vínculo de número (`aprovarVinculo`/`recusarVinculo`, nascem do WhatsApp), exportação e anonimização LGPD (`GET /clientes/{id}/exportacao`, `DELETE /clientes/{id}/dados`), último atendimento e crédito na lista (vêm com a agenda e o financeiro), ordem personalizada de colunas (o site real ainda não tem `useOrdem`), admin com permissão de Clientes (o servidor só tem dono e profissional).

## Parte 3 (feita): serviços (v82)
- **Servidor** (`backend/.../servicos/ServicoService` + `ServicoController`; migração `V11__servico_completo.sql`): `GET /api/servicos`, `GET /api/servicos/{id}`, `POST`, `PUT`, `DELETE`. Leitura: dono e profissional (profissional só vê os ativos; inativo = 404). Escrita: só o dono (403). Outra loja = 404. Regras = as de `servicos.salvar`/`remover` da API simulada, com as mesmas mensagens.
- **Campos:** `nome` (≤ 100), `codigo` (≤ 20, `[A-Za-z0-9._-]`, único por loja sem diferenciar maiúsculas; vazio = próximo número; 409 "Já existe serviço com o código X."), `categoria` (≤ 30), `preco` 0–100 mil, `duracaoMin` > 0 e ≤ 1440 (vários dias: até 14400), `intervaloMin` 0–1440, `antecedenciaH` 0–8760, `comissaoPct` 0–100, `multiDia`, `combo` + `componentes`, `ativo`. A migração V11 ampliou o intervalo (era ≤ 120) e criou `antecedencia_h`, `combo` e a tabela `servico_componente`.
- **Preço e duração por porte** (capacidade `precoPorPorte`, hoje `estetica_automotiva`, em `ServicoService.precoPorPorte`): `precos` e `duracoes` com os 5 portes (pequeno, medio, grande, suv, pickup) são obrigatórios; um valor único (`preco`/`duracaoMin`) vale para os 5; `preco`/`duracaoMin` guardados espelham o **médio**. Nos outros tipos a tabela é ignorada. Porte desconhecido = "Tabela de preços inválida.".
- **Combo:** de 2 a 10 serviços comuns e diferentes, da mesma loja (RLS + chave composta); combo dentro de combo e serviço inexistente = 400. Ordem dos componentes guardada.
- **Remover:** nunca usado = apaga (204; leva os componentes junto); com agendamento ou dentro de um combo = só desativa (200 `{"desativado": true}`). Em PUT, campo ausente (categoria, intervalo, antecedência, comissão, vários dias, combo, ativo, tabelas) não muda; preço e duração vão sempre.
- **A API simulada** passou a validar o valor único como a tabela (duração acima de 24 h sem vários dias recusada também sem tabela; "Informe a duração." sem sufixo quando falta o valor).
- **Equivalência simulada × real:** `backend/src/test/resources/equivalencia/servicos.json` (36 casos) roda na API simulada (`tests/servicos-equivalencia.test.mjs`) e no servidor (`ServicosEquivalenciaTest`, CI). Os nomes de campo do arquivo são os da API real (`duracaoMin`, `intervaloMin`); a simulada usa `duracao` e `intervalo`.
- **Tela** (`src/ui/real/Servicos.jsx`, menu Início/Clientes/Serviços): lista em cartões com busca (nome, código, categoria), novo, editar, preço e duração por porte (estética) ou únicos (barbearia), combo com os serviços comuns, vários dias (só no tipo que tem), remover com confirmação na própria tela, profissional só consulta (formulário travado, sem comissão). Teste de navegador: `tests/e2e40.mjs`.
- **Fora desta parte (chegam com os módulos deles):** notificações próprias do serviço, confirmação do serviço, materiais (estoque), grupo/Pix de cancelamento (financeiro). Com a agenda real entram: trava de mudar duração que sobreponha confirmados (hoje a duração é copiada para o agendamento na marcação, então nada se sobrepõe), antecedência mínima na marcação, expansão do combo e dados do serviço congelados no agendamento (`agendamento_servico` guarda a referência; apagar só desativa).

## Parte 4 (feita): equipe (v83)
- **Servidor** (`backend/.../equipe/UsuarioService` + `UsuarioController`; migração `V12__equipe_completa.sql`): `GET /api/usuarios`, `GET /api/usuarios/{id}`, `POST`, `PUT`, `PUT /{id}/atendimento`, `POST /{id}/senha-temporaria`, `DELETE`, `PUT /me/foto`. **Só o proprietário** cadastra, altera, refaz senha, remove e vê a lista (com contatos e CPF mascarado; a ficha traz CPF completo e nascimento). Regras e mensagens = as de `equipe.*` da API simulada. Os endpoints antigos `/api/profissionais` ficam (lista simples de quem atende e criação rápida usada nos testes).
- **Quatro perfis no servidor:** `dono`, `admin`, `atendente`, `profissional` (a V12 ampliou o CHECK de `papel`). `papel` vai no JWT como antes.
- **Permissão por seção** (`seguranca/Permissoes`, bean `@perm`): espelho de `pode()` de `rules.js`. Dono pode tudo; os demais começam pelo padrão do perfil (profissional: agenda e clientes; atendente: agenda, clientes e serviços; admin: nada) e a escolha explícita do proprietário (`usuario.permissoes`, true/false) vale por cima. Relatórios não é liberável. A checagem **lê o banco a cada chamada**: liberar/bloquear vale na hora e quem foi desativado perde o acesso mesmo com token ainda válido. Aplicada em: Clientes (`clientes`), Serviços (ler = todo perfil; escrever = `servicos`), Agenda e Escala (`agenda`; gravar o expediente da loja = `estabelecimento`). Admin e atendente passam a ver a agenda de todos (`Permissoes.veTudo`); o profissional continua só na dele. Comissão do serviço: só o dono grava (para os outros o campo é ignorado, como na simulada).
- **Sessão:** o login e a troca de senha devolvem também `secoes` (as seções liberáveis que a pessoa pode usar) e `id`; o menu do site mostra só o que a pessoa acessa (o servidor confere de novo em cada rota).
- **Senha:** nunca vem do cliente. Criar e "refazer senha" geram uma **senha temporária no servidor** (12 caracteres sem ambíguos, `auth/Temporarias`), devolvem **uma vez** (`Cache-Control: no-store`) e marcam troca obrigatória; a pessoa confirma a temporária, escolhe o próprio usuário e a senha definitiva (v80). O usuário inicial sai do apelido (`utana`, `utana2`...) ou do campo `usuario` opcional. A tela mostra a senha só até "Anotei"; nada em storage/URL.
- **Dados pessoais:** CPF, e-mail, telefone e nascimento cifrados (AES-256-GCM, como em clientes); CPF e e-mail têm hash amarrado à loja só para impedir duplicidade; apelido único sem diferenciar maiúsculas. CPF precisa de dígitos verificadores ("CPF inválido."), telefone de DDD. Campos opcionais no servidor (o assistente de início cria só o nome).
- **Regras de equipe:** não remove a si mesmo; não remove nem rebaixa o único dono ("É preciso ter pelo menos um dono."); quem tem agendamento (qualquer um, mesmo antigo) **não é removido**, só deixa de atender; deixar de atender com agendamento futuro a confirmar/confirmado é recusado com a contagem. Cor da pessoa: menor `cor_slot` livre (0 a 35), gravada no cadastro.
- **Foto:** o servidor já guarda e valida (data URL png/jpeg/webp até 30000 caracteres, conferida pelos primeiros bytes; `PUT /me/foto`); **a tela de foto ainda não existe no site real** (fica para uma próxima atualização).
- **Equivalência simulada × real:** `backend/src/test/resources/equivalencia/equipe.json` (21 casos) roda na API simulada (`tests/equipe-equivalencia.test.mjs`) e no servidor (`EquipeEquivalenciaTest`, CI). A senha fica fora do arquivo (o executor da simulada dá uma fixa). A simulada ganhou a mensagem neutra "Escolha o perfil da pessoa." (antes citava o rótulo do tipo).
- **Tela** (`src/ui/real/Equipe.jsx`, item Equipe do menu, só proprietário): lista, nova pessoa, editar (perfil, atende, vende, comissão, permissões "padrão/liberado/bloqueado" por seção), parar/voltar a atender, refazer senha, remover com confirmação na tela. Teste de navegador: `tests/e2e41.mjs`.
- **Fora desta parte:** foto na tela; escala por profissional na tela (a rota já existe, entra com a agenda); exportação/anonimização LGPD; recuperação de senha por código (sem canal configurado, o proprietário refaz a senha aqui).
